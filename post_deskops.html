DeskOps — Full-Stack IT Helpdesk & ERP System with RAG-Powered AI

Project Background

  • DeskOps was initiated in September 2024 as a solo self-guided project, developed entirely from scratch on a local WAMP stack (Windows, Apache, MySQL, PHP). The motivation was to build a realistic, production-grade IT helpdesk and ERP platform that goes beyond typical prototype quality.
  • The project grew iteratively from a structured ticketing system into a full-stack platform spanning incident management, ERP financials, knowledge management, and an AI research layer. Every module was designed and built independently, with no third-party frameworks or SaaS shortcuts.
  • The AI component was the most technically ambitious part of the build. Rather than integrating a generic chatbot, the goal was to build a genuine RAG (Retrieval-Augmented Generation) pipeline that could index ticket attachments, retrieve semantically relevant chunks, and generate grounded, cited resolution notes with evidence traceable to source documents.
  • The system is designed around ITIL principles, with structured support tiers (Tier 1–4), role-based access control, SLA enforcement, and escalation workflows. These aren't cosmetic — they govern what each user can see, do, and access throughout the platform.
  • On the ERP side, a full Financials module was built covering Invoices, Expenses, Ledger, Budget, Chart of Accounts, and an SVG-based analytics dashboard — making DeskOps more than just a helpdesk and demonstrating how both functions can coexist in a single system.

Project Objective


  • The primary objective was to build a functioning IT helpdesk from scratch that could realistically support a small-to-medium IT operations team. This meant covering the full incident lifecycle: ticket creation, triage, assignment, escalation, SLA tracking, resolution, and post-closure documentation.
  • A secondary objective was to explore how AI could be integrated into an operational IT context in a meaningful way — not as a novelty, but as a genuine productivity tool. This led to the development of the Ask AI tab, the RAG pipeline, and the AI-generated resolution notes feature.
  • The most challenging objective was the two-pass citation system for resolution note generation. The goal was to produce structured notes grounded in actual evidence from indexed attachments, with citations that link specific factual claims to their source documents. This required building a pre-screening pass to filter RAG chunks for relevance before passing them to the generation model.
  • From a research perspective, the platform was also used to investigate AI causal reasoning — one of the first research tickets raised through the system explored the gap between correlation-based AI decision-making and genuine causal understanding. The RAG pipeline retrieved and indexed academic papers by Judea Pearl and others, surfaced inline citations, and produced a structured resolution note grounded in the evidence.

Key Modules & Features


  • Full ticket lifecycle management: creation, triage, assignment, escalation, and closure.
  • Role-Based Access Control (RBAC) across five tiers: Admin, Tier 1, Tier 2, Tier 3, and Tier 4. Each tier has scoped views, permissions, and escalation paths.
  • SLA tracking with color-coded urgency indicators. SLA timers run per ticket and trigger visual alerts as breach thresholds approach.
  • Ticket tags with AI-generated tag profiles — each tag has a short summary, context text, signals, recommended actions, examples, and facets stored in structured JSON. These profiles are used to enrich resolution note generation.
  • Comment system supporting user comments and system-generated comments, with Markdown rendering and attachment linking.
  • Attachment manager with gallery preview, password protection, bundle management (zip grouping), and per-file ChromaDB indexing status.


  • Attachments are indexed into ChromaDB via Python scripts that chunk documents, generate embeddings using the ChromaDB client-side embedding model, and upsert vectors with rich metadata (source name, ticket ID, attachment ID, chunk index).
  • The Ask AI tab provides a per-ticket chat interface. Each conversation is stored as a named session. Users can switch between sessions, create new ones, and delete old ones — with session history persisted in MySQL and messages linked by session ID.
  • The AI uses a multi-model fallback chain: Gemini 2.5 Flash → Gemini 2.0 Flash → Gemini 2.0 Flash Lite → NVIDIA NIM (Gemma 4 31B) → Groq (Llama 3.3 70B). Each model gets one retry on rate limits before falling back to the next. The UI shows a live countdown timer during rate-limit waits.
  • Source citations are rendered as inline superscripts in the chat. The sources sidebar shows indexed attachments with their status (indexed, pending, not indexable) and allows per-file or bulk indexing directly from the tab.
  • Ticket description and comments are indexed as text chunks alongside file attachments, so every aspect of the ticket is queryable.


  • A dedicated Generate with AI button in the Resolution Notes section triggers a two-pass AI pipeline against the ticket's RAG context, tag profiles, and comment history.
  • Pass 1 — Citation Screening: All RAG chunks retrieved for the ticket are sent to the AI with a structured relevance screening prompt. The AI evaluates each excerpt and returns a JSON array indicating whether each citation is relevant to the ticket topic and what specific factual claim it supports. Irrelevant chunks are filtered out before Pass 2. If Pass 1 returns zero relevant citations, the full chunk set is used as a fallback to prevent empty notes.
  • Pass 2 — Note Generation: The pre-screened citations are passed to the AI alongside the ticket description, tag intelligence, and comment history. The system prompt embeds three silent diagnostic frameworks: Cynefin domain classification (to calibrate tone and complexity), Bloom's Taxonomy level (to calibrate depth), and DOT research strategy (to determine the appropriate evidence approach). The AI writes the note without ever outputting the framework reasoning.
  • Citations appear as inline superscripts [N] within the note. A collapsible citations panel below the editor lists each source with the supporting quote. Citations are persisted to MySQL and re-rendered on page reload.
  • The note follows a structured format: Resolution Note → INITIAL PROBLEM (with Key Actions Taken) → ADDITIONAL CONTEXT (with Summary, Stabilization Work, and either Outcome or Open Questions depending on whether a confirmed resolution is detected in the comments).


  • Full double-entry bookkeeping system with a Chart of Accounts, General Ledger, and automatic journal entries on invoice and expense creation.
  • Invoice management: create, edit, mark as paid/unpaid, generate PDF-ready views. Invoices auto-post to the ledger on status change.
  • Expense tracking with category assignment, supplier information, and ledger integration.
  • Budget module: set budget targets per account category and track actuals against budget in real time.
  • SVG-based analytics dashboard with revenue vs expense charts, budget utilization gauges, and ledger balance summaries — all rendered server-side without external charting libraries.
  • Full PHP 8 bind_param compliance throughout, with typed local variables and Throwable catch blocks on all database operations.


  • Structured knowledge article management with rich text editing, article categorization, and tagging.
  • AI-assisted tag profiling: when a tag is created or updated, the system can generate a structured profile (context, signals, recommended actions, examples, synonyms, facets) using the LLM chain. These profiles are stored in JSON and used to enrich resolution note generation.
  • Articles are searchable and surfaceable during ticket handling, providing agents with contextual self-service material during incident resolution.


  • Admin-only interface for inspecting the ChromaDB vector store. Shows total chunk count, indexed sources grouped by ticket and attachment, and source metadata.
  • Supports filtering by ticket ID, deleting all chunks for a specific attachment, and wiping all indexed content for a ticket.
  • Test Query panel: enter a ticket ID and a question to run a live semantic query against ChromaDB and inspect the retrieved chunks with distance scores.
  • Start ChromaDB button: if the vector store is offline, the admin can start the ChromaDB server process from within the app via a PHP shell call, with a live status indicator and auto-reload on success.


In Action

The first research ticket raised through the system investigated AI causal reasoning — specifically, the gap between correlation-based AI decision-making and genuine causal understanding. Four academic papers by Judea Pearl, Geirhos et al., and others were indexed as attachments. The RAG pipeline retrieved relevant chunks, Pass 1 screened them for relevance to the ticket topic, and Pass 2 generated a structured resolution note grounded in the evidence with inline citations.

Four of twelve planned research questions were explored in Episode 1:

  • To what extent do current AI agents rely on correlation rather than causal reasoning?
  • How can we detect when an agent is using spurious correlations instead of meaningful relationships?
  • Are there reliable indicators that distinguish causal reasoning from pattern matching in model outputs?
  • How does shortcut learning manifest in multi-step agent workflows?
