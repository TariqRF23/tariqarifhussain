Executive Summary

The case for multi-cloud, distilled

Relying on a single cloud provider is a risk financial institutions cannot absorb. This architecture splits the stack across AWS and Azure so neither provider becomes a single point of failure, and every layer — network, compute, database, traffic — has an independent failover path.

Challenge
Single-provider risk in a 24/7 business
  • Regional outages cause measurable revenue loss and reputational damage
  • Peak-hour demand spikes overwhelm fixed-capacity infrastructure
  • Sensitive customer data requires multi-region residency and GDPR compliance
  • Regulatory audits demand verifiable disaster recovery capability
Solution
Active-active multi-cloud with cross-cloud replication
  • Front-end on Azure VMs with Traffic Manager for global routing
  • Back-end processing on AWS EC2 behind SQS for async decoupling
  • RDS Multi-AZ primary with cross-cloud sync to Azure SQL Database
  • DNS-level failover via Route 53 & Azure Traffic Manager health checks
Outcome
Resilient, compliant, cost-aware at any scale
  • 99.99% uptime target with measured <15min RTO across regions
  • Autoscaling handles 10× peak load without manual intervention
  • Encrypted at rest and in transit; IAM + Azure AD enforce least-privilege
  • Runbook-tested failover drills confirm recovery procedures quarterly

Design Decisions

Why each architectural choice was made

Every major component in this architecture was selected for a specific reason. These are the decisions that shape the trade-offs between cost, resilience, latency, and operational complexity.

Active-active, not active-passive
Both clouds serve live traffic simultaneously via DNS-weighted routing. Neither side sits idle waiting for a failure.
Passive failover wastes 50% of capacity and tends to fail the first time it's tested. Active-active continuously exercises both paths.
SQS between front-end and back-end
Customer requests queue asynchronously. Front-end stays responsive during back-end slowdowns; back-end scales independently of incoming request rate.
Tight coupling propagates slowness. A queue absorbs spikes, smooths throughput, and gives each tier its own operational tempo.
RDS Multi-AZ primary, Azure SQL replica
RDS Multi-AZ handles fast in-region failover (seconds). Cross-cloud replication to Azure SQL handles catastrophic regional loss (minutes).
Two independent failure domains. Most outages are regional, not global — using the right tool for each scope cuts RTO significantly.
Tiered subnets: public / app / DB
Public subnet holds only the load balancer. App tier in private subnet. Database tier in a separate private subnet with no route to the internet.
Defense-in-depth. A compromised EC2 instance cannot reach the database directly without traversing a NACL and security group boundary.
KMS + Key Vault instead of shared secrets
Encryption keys stored in AWS KMS and Azure Key Vault, never in application config. Rotation handled by the cloud provider, audit trails built in.
Hardcoded secrets leak via logs, repos, and backups. Managed key services solve rotation, audit, and access control in one integrated layer.
DNS failover via health checks
Route 53 and Azure Traffic Manager poll endpoint health continuously. Unhealthy endpoints drop out of DNS within 30 seconds — no manual intervention.
Human-operated failover takes minutes or hours. Automated DNS failover takes seconds and doesn't require someone to be awake.
Architecture Layers

Seven layers, each with its own failure mode

Each layer is designed to fail independently. A compute outage doesn't take down the network. A database failover doesn't interrupt monitoring. This isolation is what makes the overall system resilient.

  • AWS VPC and Azure VNet provide isolated network environments for every service tier
  • Public/private subnet segregation — databases and internal services sit in private subnets with no direct internet exposure
  • Site-to-site VPN tunnels between AWS and Azure enable encrypted, authenticated cross-cloud communication
  • Firewall rules and security groups enforce least-privilege traffic flow at every network boundary
  • Encryption at rest via AWS KMS and Azure Key Vault; TLS 1.2+ in transit for every service-to-service call
  • Identity federation via AWS IAM and Azure Active Directory with role-based access controls

Request Lifecycle

How a customer request travels across clouds

A single loan application traverses both clouds, passes through a queue, touches multiple data stores, and generates telemetry — all before the customer sees a response. Each step is decoupled so a failure at any layer doesn't cascade.

1
Customer initiates request
Traffic enters the system via DNS resolution. Route 53 and Azure Traffic Manager perform health checks and route to the healthiest cloud endpoint.
Route 53 · Azure Traffic Manager
2
Load balancer distributes to front-end
Request hits the regional load balancer, which distributes across healthy front-end instances based on current capacity and response times.
Azure Load Balancer · AWS ELB
3
Front-end queues for async processing
Azure VM front-end validates the request, authenticates via Azure AD, and places the payload onto AWS SQS. Front-end returns a tracking ID immediately — no blocking.
Azure VMs · Azure AD · AWS SQS
4
Back-end consumes and processes
AWS EC2 workers poll SQS, retrieve the message, and begin transactional processing. Visibility timeout ensures the message is reprocessed if a worker fails mid-task.
AWS EC2 · SQS visibility timeouts
5
Data read/write against RDS
Back-end reads customer history from the RDS primary, performs validation and risk calculations, and writes the result within an ACID transaction.
RDS Primary · ACID transactions
6
Cross-cloud replication to Azure SQL
Committed writes replicate asynchronously to Azure SQL Database across the VPN tunnel. Replica lag monitored continuously; alerts fire if lag exceeds threshold.
Cross-cloud sync · Replica lag monitoring
7
Response routed back to customer
Back-end publishes the processed response to SQS. Front-end polls for completion and delivers the final result to the customer's browser.
SQS response queue · Azure VMs
8
Telemetry captured end-to-end
CloudWatch and Azure Monitor capture metrics from every hop — response times, queue depth, DB performance. Dashboards update in real-time; anomalies trigger alerts.
CloudWatch · Azure Monitor · Unified dashboards

Implementation

Phased rollout over six stages

A multi-cloud migration follows a strangler-fig pattern — the new architecture grows around the existing one piece by piece. Each phase is independently testable and reversible before moving forward.

1
Core Infrastructure
VPC, VNet, load balancers, and VPN tunnels. Establishes the secure network foundation.
2
Front-End Services
Customer-facing Azure VMs. Configure SQS for async request queueing.
3
Back-End & Data
Deploy AWS EC2 back-end with RDS. Set up cross-cloud replication to Azure SQL.
4
Monitoring
Wire up CloudWatch and Azure Monitor. Configure alerts and autoscale triggers.
5
DNS Failover
Deploy Route 53 and Azure Traffic Manager. Run failover drills in staging.
6
Optimization
Tune autoscaling. Run performance tests under load. Establish quarterly DR drills.
