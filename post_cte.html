A wise CTE: IT governance in database updates

How to change rows in a production table without becoming the reason for the incident. Written for whoever has to approve the change as much as for whoever runs it.

  • SubjectDatabase operations
  • AudienceIT operations management
  • Dated23 September 2024
  • LengthForty-four pages, with an appendix of scripts

The job

A table called project_data is live. Three clients need their project and project manager values corrected. That is the entire task, and it is the kind of task that takes a company down when somebody does it from memory at the end of a Friday.

Governance, which is not paperwork

Four controls, each of which exists because of a specific failure. Segregation of duties, so the person who writes a change is not the only person who approves it. Peer review before it runs. Documentation and auditing, so the change can be explained afterwards. And testing in a staging environment, so the first time the statement executes is not in production.

Regulatory non-compliance belongs on that list as much as data corruption does. The difference is that corruption announces itself and non-compliance does not, until somebody asks for the audit trail of a change made eighteen months ago.

The order it has to happen in

Why a common table expression

The alternative is one UPDATE statement per client, run in sequence, each one its own chance to fat-finger a WHERE clause. A CTE puts the intended new values in one readable block, joins them to the live table on the key, and updates in a single statement that a reviewer can check by reading rather than by simulating.

WITH project_data_cte AS (
    SELECT 'Client1' AS client, 'Project A' AS project, 'PM X' AS PM
    UNION ALL
    SELECT 'Client2' AS client, 'Project B' AS project, 'PM Y' AS PM
    UNION ALL
    SELECT 'Client3' AS client, 'Project C' AS project, 'PM Z' AS PM
)
UPDATE pd
SET
    pd.client  = cte.client,
    pd.project = cte.project,
    pd.PM      = cte.PM
FROM project_data_cte AS cte
INNER JOIN project_data AS pd
    ON pd.client = cte.client;

The reviewable property is the point. Everything that is about to change is written out as literal values in one place, so a reviewer compares the block against the request rather than against the schema.

Backing up only what you touch

Not the table. The rows. A full backup of a large production table before a three-row change is the sort of thing that turns a five-minute window into a ninety-minute one, and then gets skipped next time because of it.

SELECT client, project, PM
INTO backup_schema.project_data_backup
FROM project_data
WHERE client IN ('Client1', 'Client2', 'Client3');

The transaction around it

Backup and update go inside one transaction, so the state after a failure is the state before the attempt. Either both happened or neither did, which is the only version of this that can be explained in an incident review.

BEGIN TRANSACTION;

-- back up the rows about to change
SELECT client, project, PM
INTO backup_schema.project_data_backup
FROM project_data AS pd
WHERE pd.client IN ('Client1', 'Client2', 'Client3');

-- then the update, through the CTE above

COMMIT;          -- on success
ROLLBACK;        -- on anything else

For longer sequences the report uses savepoints, so a partial rollback is possible without discarding work that already succeeded. That matters when the update is one step in a batch and the failure is in step four of six.

Timestamps, which make the window recoverable

A rollback that restores every row from a backup is blunt: it also reverts anything legitimate that happened in between. A timestamp on each row turns the rollback into a window, so what gets reverted is what this change touched, in the minutes it touched it.

ALTER TABLE project_data
ADD update_timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP;
UPDATE pd
SET
    pd.client  = backup.client,
    pd.project = backup.project,
    pd.PM      = backup.PM
FROM backup_schema.project_data_backup AS backup
INNER JOIN project_data AS pd
    ON pd.client = backup.client
WHERE pd.update_timestamp >= '2024-09-10 10:00:00';

The practices around it are short and worth repeating. Keep the timestamp automatic, because a timestamp somebody has to remember to set is a timestamp that is sometimes missing. Keep the timezone consistent, because a rollback window computed in the wrong zone reverts the wrong hour. Archive old logs on a schedule. And feed the whole thing into whatever monitoring already exists, rather than leaving it as a column nobody reads.

Generating the SQL from a spreadsheet

The list of changes usually arrives as a spreadsheet, because that is what the business works in. Rather than retyping it into SQL, which is where transcription errors come from, the report generates the statements from the sheet itself.

="UPDATE project_data SET client = '"&A2&"', project = '"&B2&"', PM = '"&C2&"' WHERE client = '"&A2&"';"

It scales to a thousand rows as easily as to three, and it removes the step where a human reads a cell and types what they think it said. The discipline around it is the same discipline as everywhere else here: validate the data types, read the generated statements before running them, test in staging, and keep the sheet with the change record so the generated SQL can be explained later.

What it is really about

None of this is clever. A CTE, a backup of three rows, a transaction, a timestamp column and a spreadsheet formula are all ordinary. What the report argues is that the ordinary version, performed in the right order with a way back at every step, is what separates a routine change from an incident, and that the ordering is a governance question rather than a technical one.
